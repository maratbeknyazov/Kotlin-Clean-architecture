# Laboratory 4 Clean architecture

## Идея работы

Я разделил MovieShelf на три слоя. `presentation` показывает экран и хранит его состояние. `domain` содержит модели и правила работы с фильмами. `data` получает и сохраняет данные. Конкретные объекты создаются в `AppContainer`.

Для меня основная идея Clean Architecture такая: правило сортировки не должно зависеть от того, где лежат фильмы. Поэтому use case работает с интерфейсом `MovieRepository`, а не с конкретным хранилищем.

## Tasks 1–6

1. Создан проект MovieShelf, пакет `uz.ttpu.movieshelf`, Minimum SDK 24. Есть пакеты `data`, `presentation`, `di` и отдельный модуль `domain`. Создан локальный Git-репозиторий.
2. `MovieDto` содержит поля источника данных: `releaseYear` и `score`. `MovieRemoteDataSource` описывает загрузку, а `MovieLocalDataSource` — кеш и избранное. Имитация сети ждёт 800 мс и может выбросить `IOException`. `suspend` позволяет приостанавливать ожидание, чтобы I/O не блокировал главный поток. Сам по себе `suspend` не переносит блокирующий код в другой поток.
3. `Movie` содержит понятные приложению поля `year` и `rating`. `toDomain` переводит DTO в Movie и добавляет признак избранного. Mapper находится в `data`, потому что `domain` не должен знать о DTO.
4. Репозиторий сначала читает ID избранных фильмов. При успешном запросе он обновляет кеш. При `IOException` от сети использует кеш. Если кеша нет, ошибка передаётся дальше. Отмена корутины не перехватывается. Избранное всегда берётся из локального хранилища.
5. `GetMoviesUseCase` сортирует рейтинг по убыванию, затем название по алфавиту. Зависимость от `MovieRepositoryImpl` была бы ошибкой: внутренний `domain` зависел бы от внешнего `data`. Это объяснение записано в комментарии над use case.
6. Интерфейс `MovieRepository` находится в `domain`. Use case зависит от него, а `MovieRepositoryImpl` реализует его. Импортов слоя `data` в исходниках `domain` нет.

## Tasks 7–9

7. `MovieListUiState` имеет Loading, Success и Error. ViewModel публикует read-only StateFlow. Refresh запускает загрузку; повторная загрузка отменяет предыдущую. Нажатие на сердце меняет один фильм без повторного запроса к сети.
8. `MovieListScreen` получает состояние и callbacks. Есть спиннер, ошибка с Retry, список с Refresh и баннер кеша. Ключ элемента LazyColumn — ID фильма. У сердца есть описание действия для доступности. Добавлены четыре Preview: загрузка, успех, кеш и ошибка.
9. `AppContainer` вручную создаёт источники, репозиторий и use cases. `MovieShelfApp` создаёт контейнер один раз для приложения. Activity связывает ViewModel и экран. Переключатель имитации сети находится в Activity, потому что это место соединения конкретных объектов.

Первый ожидаемый порядок: Echoes of Khiva, Registan Rhapsody, The Silk Road Express. У последних двух одинаковый рейтинг 8.4, поэтому решает название.

ViewModel хранит выбранный фильтр, экран показывает FilterChip Favorites only. Если снять сердце в списке избранного, фильм сразу удаляется из видимого списка.

Два новых теста проверяют фильтрацию с сохранением сортировки и кеша, а также пустой результат. Ещё три теста ViewModel проверяют обновление сердца без сети, исчезновение фильма из избранного с последующим отключением фильтра и Retry после ошибки.

## Task 15

Комментарий в начале `MovieListViewModel.kt` объясняет вызовы и зависимости.

Порядок вызовов: MovieItem → MovieListViewModel → ToggleFavoriteUseCase → MovieRepositoryImpl → SharedPrefsMovieLocalDataSource.

Зависимости устроены иначе: use case знает интерфейс MovieRepository из domain. Реализация репозитория зависит от этого интерфейса, хотя при выполнении use case вызывает реализацию через него. Это Dependency Inversion. Аналогично репозиторий знает интерфейс локального источника. Сам MovieItem получает callback; прямой зависимости от ViewModel у него нет.

Use case не может вызвать `Log.d`, потому что domain не имеет Android в classpath. Для постоянного логирования можно объявить интерфейс Logger в domain и передать реализацию из внешнего слоя.

Проверка Logcat выполняется на устройстве. Временно добавь:

| Место | Строка перед действием |
| --- | --- |
| Callback IconButton в MovieItem | `Log.d("CleanFlow", "UI: heart click")` |
| Начало onFavoriteClick | `Log.d("CleanFlow", "Presentation: favorite click")` |
| Начало ToggleFavoriteUseCase.invoke | `println("CleanFlow: Domain: toggle favorite")` |
| Начало MovieRepositoryImpl.toggleFavorite | `Log.d("CleanFlow", "Data: toggle favorite")` |
| Начало SharedPrefsMovieLocalDataSource.setFavorite | `Log.d("CleanFlow", "Local: save favorite")` |

В MovieItem замени `onClick = onFavoriteClick` на лямбду, которая пишет лог и затем вызывает `onFavoriteClick()`. В файлах `app` добавь `import android.util.Log`. В domain используется только println. Нажми сердце и найди CleanFlow в Logcat. После проверки убери временные строки и снова запусти тесты.
